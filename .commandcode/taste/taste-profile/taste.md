# Taste Profile
- Prefers to communicate in Indonesian (Bahasa Indonesia). Confidence: 0.9
- Wants the assistant to thoroughly explore and understand the existing codebase/module (structure, patterns, conventions, dead code) before making any modifications. Confidence: 0.8
- Test cleanup must guarantee all data created during the test run is deleted after the entire suite finishes (in `afterAll`), regardless of whether individual tests pass or fail — including auto-generated related records, not just the primary one (e.g., creating a location auto-creates an office, so both the office id and location id must be tracked and both deleted) to avoid leaving orphan data. Confidence: 0.95
- When writing UI test selectors, prefers the assistant to explore the live app directly via browser automation and verify/probe selectors against the real page — not guess from code or rely on screenshots/docs alone (explicitly chose direct exploration over screenshots or manual flow docs; the user's flow-spec instruction sheet also recommends probing the live app to verify selectors before writing code). Confidence: 0.9
- Prefers env-driven test config: URLs and credentials must come from `.env` (e.g., `HRIS_WEB_URL`, `ADMIN_EMAIL`/`ADMIN_PASSWORD`) with relative paths in test code — no hardcoded staging URLs or fallback credentials in specs/setup (approved refactor to remove them; user explicitly instructed to use account info from the project's `.env` when authoring tests). Confidence: 0.9
- Prefers UI tests structured with Page Objects (a BasePage + one page class per module, barrel-exported) following the documented POM convention. Confidence: 0.7
- Treats flaky test failures as bugs to fix: when a test fails intermittently in the report, expects root-cause investigation (re-run to reproduce, probe the live app to observe actual behavior) and verification of the fix with repeated runs (e.g., `--repeat-each`) until stable. Confidence: 0.7
- Prefers positive success verification over negative assertions: verify a save succeeded by waiting for the success toast (e.g., "Your data has been successfully saved.") rather than asserting error text count is 0 (e.g., `toHaveCount(0)` on "is required") — negative assertions are flaky when client-side validation messages flicker transiently. Confidence: 0.6
- Wants documentation organized by concern/type rather than one monolithic doc: e.g., test guides split into separate markdown files per testing type (API testing guide, UI testing guide) with a concise index file that links them and holds shared conventions. Confidence: 0.7
- Wants guides and documentation to be written to match the actual code patterns already implemented in the project — grounded in real specs, fixtures, configs, and folder structure (e.g., "sesuai dengan code pattern yang telah diimplementasikan di proyek ini") — not generic or idealized templates. Confidence: 0.8
- Intends to author UI automation scripts by recording flows with a manual recording tool (e.g., Katalon Studio or similar browser-extension recorders), treating the raw recording as a draft that must be cleaned up/refactored into the project's structured conventions (Page Objects, semantic selectors, unique data, naming patterns) before it is considered final. Confidence: 0.8
- Is also open to having AI author the UI automation scripts, expecting the AI to be given concrete inputs upfront — business flow description (step-by-step), live app access (URL + credentials), test data (valid + negative), verification points (toast/heading/URL), and priority/tags — and to probe the live app for accurate selectors rather than guessing. Confidence: 0.5
- Prefers to formalize the AI handoff as a reusable markdown template in the repo (e.g., `docs/ui-flow/ui-flow-template.md`), one filled-in spec per flow, capturing: general info (name/tags/role/output files), step-by-step business flow with UI labels verbatim, app access checklist, test data (valid + negative), verification points, special notes, and references for the AI to read — so AI can generate structured scripts from it. Confidence: 0.6
- Prefers to manage the AI handoff specs as spreadsheets (Google Sheets / Excel) for tracking many flows — multi-sheet structure (Flows master one row per flow, Steps detail with one row per action, Test Data, Instructions) linked by a `flow_id` key, with columns for priority/tags, role, expected output files, verification points, action types (`click`/`fill`/`select_option`/`datepicker`/`combobox_search`/`verify_visible`...), and value references (`data_key` or `env:VAR`). Confidence: 0.7
- Treats the flow-tracking Excel (e.g., `docs/ui-flow/office-list.xlsx`) as the authoritative, live source of truth for test scope: when the user says scenarios were added, re-read the file (not the previously analyzed version) and generate scripts only for flows whose `Status` is "In Progress", leaving "Done" flows untouched (do not re-create scripts for already-covered flows). Confidence: 0.9
- Requires the assistant to read the project's test guides/documentation before writing any test scripts — root test guide markdown plus module-specific guides (e.g., `docs/ui-testing-guide.md`) must be read first (explicit instruction: "Pastikan sebelum membuat testing skripnya, anda perlu membaca test guide markdown di root project dan @docs\ui-testing-guide.md"). Confidence: 0.9
- Prefers the AI to author the test scripts and, by default, leave test execution to the user (per the flow spec's Instructions sheet: don't run the test scripts, deliver verified-compiling code) — but when the user explicitly asks for a run, the AI should execute the tests and verify results. Confidence: 0.4
- When asked to run tests, prefers scoped runs limited to the requested module/spec (e.g., `npx playwright test --project=Hris-Ascendiz-UI office-list`) rather than the full suite. Confidence: 0.7
- Keeps test specs organized by module, NOT by flow status: status (Done / In Progress) from the flow Excel must be a marker/label/tag (e.g., comment or describe-suffix like `[Done]` / `[In Progress]`) indicating what still needs work — never the basis for splitting a module across multiple files. All flows of a module (e.g., OL-001 s/d OL-015) belong in a single coherent spec file, and separate-by-status files (e.g., `<module>-in-progress.spec.ts`) should be merged back into the one module file. Confidence: 0.9
- When tests run in parallel (fullyParallel with multiple workers), avoids asserting against row position (e.g., `rows.first()` to assume the just-created record is at the top of the list) because another worker's test may write data concurrently; instead resolves the row by its unique name (e.g., `rowByLocationName(name)`), which is robust to parallelism. Confidence: 0.8
- For guaranteed post-suite data cleanup, prefers looking up created records by name via the API list endpoint in `afterAll` (then deleting them) over capturing ids at runtime with `page.on('response')`, because response-id capture is unreliable across workers/hooks; the API request context must set an explicit `baseURL` (e.g., `HRIS_API_URL`) since relative paths fail without it. Confidence: 0.5

- Wants deployment/ops setup guides written as step-by-step markdown documentation committed in the repo's `docs/` folder (so it's versioned alongside the code, usable as a checklist e.g. `docs/deployment-jenkins.md`), rather than kept only as internal plan files; and expects this doc to be continuously kept current by appending new steps/how-to answers as new topics come up (e.g., asking to add module-specific trigger steps to the existing md).
